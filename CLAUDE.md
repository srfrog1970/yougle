# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Yougle: a privacy-focused, decentralized text messenger. No accounts, no phone numbers, no push notifications, no shared third-party messaging infrastructure. Every user gets an automatic client-side **Local** mailbox; anyone can optionally run a self-hosted, single-tenant **Server** mailbox (`pm-node`) for durable async delivery. Connectivity (not messaging) still depends on n0's public iroh relay/discovery infrastructure — see `docs/THREAT-MODEL.md`.

Product requirements are locked in `docs/PRD.md` (read this before changing user-facing behavior — flows, mailbox model, delivery semantics, and explicit MVP scope limits like no groups/attachments/multi-device are all defined there, including *why* the design changed from v1.0 to v2.0). Wire format is specified in `docs/PROTOCOL.md`. Security posture and known gaps are in `docs/THREAT-MODEL.md`. Each crate's own README documents its scope and milestone status in more depth than this file does — read the relevant one before working in a crate.

## Build & test commands

Building requires `libssl-dev` and `pkg-config` (Debian/Ubuntu: `sudo apt-get install -y libssl-dev pkg-config`) for the bundled SQLCipher build in `pm-store`.

```
cargo test                                          # run all workspace tests
cargo test -p pm-core                                # test a single crate
cargo test -p pm-core m3_exit_criteria               # run a single integration test file
cargo test -p pm-core --test m3_exit_criteria some_test_fn   # a single test function
cargo fmt --all -- --check                           # CI formatting check
cargo clippy --all-targets --all-features -- -D warnings   # CI lint check (matches .github/workflows/ci.yml)
```

CI (`.github/workflows/ci.yml`) runs exactly: `cargo fmt --all -- --check`, `cargo clippy --all-targets --all-features -- -D warnings`, `cargo test --all-features`. Run all three before considering Rust work done.

Running the Server mailbox binary locally:

```
PM_NODE_MAILBOX_KEY=<64 hex chars> cargo run -p pm-node
```

React Native app (`app/`) — see `app/README.md` for the full toolchain (uniffi-bindgen-react-native, NDK, the WSL2 CPU-affinity workaround for a kernel bug, etc.):

```
cd app && npm install
taskset -c 0-3 env CARGO_BUILD_JOBS=2 npx ubrn build android --and-generate   # rebuild bindings after touching pm-ffi
```

`app/android`, `app/ios`, `app/cpp`, `app/src/generated`, `app/src/Native*`, `app/src/index.*ts*` are generated by `ubrn` — never hand-edit them; re-run the `ubrn build` command instead.

## Workspace architecture

Seven Rust crates in `crates/`, layered bottom-up with a strict dependency direction — lower crates never depend on higher ones:

```
pm-proto      envelopes, padding, HKDF chain derivation, wire message types (node + direct protocol). No networking/storage/crypto.
pm-crypto     vodozemac (Olm) wrapper, BIP39 seed handling, identity key derivation, backup blob encryption.
pm-store      SQLCipher-encrypted local persistence, migrations, Lamport clock. Identity/crypto-agnostic — stores whatever bytes it's given.
pm-transport  iroh endpoint + NodeClient (client side of the pm-node wire protocol).
pm-node       the Server mailbox binary: in-memory + optional SQLCipher-persisted store, iroh ProtocolHandler, rate limiting, retry queue.
pm-core       Client: ties proto+crypto+store+transport together — pairing, send/sync, backup/restore, mailbox-pointer updates. The public API surface.
pm-ffi        uniffi bindings exposing pm-core to the React Native app (Turbo Modules via uniffi-bindgen-react-native).
```

`pm-proto` is shared verbatim between `pm-core` (client) and `pm-node` (server) so wire framing can never drift between the two ends.

Each crate's tests live in its own `tests/` directory as milestone "exit criteria" integration tests (e.g. `pm-core/tests/m3_exit_criteria.rs`, `pm-node/tests/rate_limit_exit_criteria.rs`) — these are the actual spec of what each milestone guarantees end-to-end, more concrete than the READMEs. When changing behavior a milestone test covers, that test is the contract to preserve or deliberately update.

### Key design points worth knowing before touching the core

- **Mailbox model**: every user has a Local mailbox (client-side, always present) and optionally one self-hosted Server mailbox. Server is preferred when present; Local is the automatic fallback. There is no shared/community mailbox — that was removed between PRD v1.0 and v2.0 (see the revision table at the top of `docs/PRD.md`).
- **Delivery semantics differ by both sides' setup** (`docs/PRD.md` §5, Flow 3): Server-mailbox recipient → durable write; both Local-only → live ~15-20s direct-connect attempt, revert to compose box on failure; sender has Server but recipient is Local-only → sender's own server retries on a schedule.
- **Olm session establishment is lazy and one-sided by design**: both sides get a one-time key from pairing, but only whichever side sends *first* calls `create_outbound_session` (see `pm_store`'s `pending_otk` and `pm-core`'s README). Both sides eagerly creating outbound sessions produces two mismatched ratchets — don't "fix" this into eager establishment.
- **Padding**: `Envelope`s are padded into fixed 256/1024/4096-byte buckets (`pm-proto/src/padding.rs`) so ciphertext length doesn't leak message length; backup blobs are padded to the next power of two (floored at 4096) for the same reason. Not everything on the wire is padded — `Fetch` responses and `Ack` requests scale with pending-message count (see `docs/THREAT-MODEL.md` §"A network observer"). Keep this distinction in mind before assuming padding covers a given wire message.
- **Mailbox-pointer updates must be signed and verified** (Ed25519, the identity key) and are ordered by a locally-persisted monotonic counter (`seq`), not wall-clock time — clock-skew-safe by construction, and the counter is included in backups so restoring a device doesn't cause its own future updates to be rejected. See `docs/PROTOCOL.md` §7 and the THREAT-MODEL "Resolved" notes for why wall-clock ordering was replaced.
- **`pm-node` write authorization** is a one-time hash-preimage (`auth = SHA256(pm_proto::derive(pair_secret, "auth", n, 32))`), not an identity or owner check — `Write` is deliberately unauthenticated-by-identity since the caller is a sender, not the mailbox owner. `RegisterSlot`/`Write` are rate-limited per authenticated iroh `EndpointId`; `Fetch`/`Ack`/`PollFailedDeliveries` are intentionally exempt (already gated by `mailbox_key`, and the app polls them continuously while foregrounded).
- **`pm-node` persistence is opt-in** via `PM_NODE_DATA_DIR` (SQLCipher-encrypted, keyed from `PM_NODE_MAILBOX_KEY`); unset, it runs fully in-memory and a restart clears anything not yet fetched/delivered.
- Several things were deliberately simplified out of the original pre-decentralization design (the full slot-hash/tag-chain anti-enumeration scheme, `REDEEM_TICKET`, fixed slot-count padding) because they existed to hide contact-graph info from a shared *community* operator that no longer exists in this architecture. Don't reintroduce that machinery without checking `docs/PRD.md`/`docs/THREAT-MODEL.md`'s Open Items first — whether any of it is still warranted for a different reason is explicitly unresolved, not settled either way.

### app/ (React Native)

`app/` is a turbo-module library wrapping `pm-ffi`; `app/example/` is the actual app (`example/src/App.tsx` entry point, `example/src/screens/` one file per PRD §7 screen, `example/src/lib/client.tsx` holds the `FfiClient` React context). All protocol/crypto logic lives in Rust — the RN layer is UI only, bridged via uniffi. See `app/README.md`'s "Other issues that only show up at runtime" section before debugging anything that passes `cargo test`/`tsc` but fails on-device (uniffi version pinning, `async_compat::Compat` wrapping, Metro `watchFolders`, Hermes missing `TextDecoder`, etc.) — these are known, already-diagnosed traps, not new bugs.

### deploy/

Docker (`Dockerfile` + `docker-compose.yml`) and systemd (`pm-node.service`) paths for self-hosting `pm-node`. `deploy/nat-sim/` simulates two isolated NATed networks (Linux network namespaces) to test real Local-to-local delivery outside a shared subnet — see its README for what it does and doesn't prove about hole-punching vs. relay fallback.

## Documentation conventions

- ADRs go in `docs/adr/`, one file per decision, numbered `NNNN-title-in-kebab-case.md`: record the decision, alternatives considered, and why, so a future reader doesn't have to re-derive the rationale.
- Crate/component READMEs record a `Status:` line (milestone, what's implemented vs. deferred) — keep it current when finishing work that changes a crate's scope.
- Docs in this repo are written to state honestly what's verified vs. assumed (e.g. `deploy/README.md`'s and `app/README.md`'s Status sections distinguish "actually run and confirmed" from "written and expected to work") — match that tone rather than overclaiming completeness in new docs.
